### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать и выключать отопление в своих домах через веб-интерфейс
- Система поддерживает обновление состояния датчиков через REST API (PATCH /api/v1/sensors/:id/value)
- Реализована возможность создания, обновления и удаления датчиков отопления
- Управление происходит синхронно - команды отправляются от сервера к датчику напрямую

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в доме через веб-интерфейс
- Система получает данные о температуре с внешнего API (Temperature API)
- Поддерживается получение данных по местоположению (GET /api/v1/sensors/temperature/:location)
- Данные температуры обновляются в режиме реального времени при запросе к датчикам
- Каждый датчик имеет статус, значение температуры, единицу измерения и время последнего обновления

### 2. Анализ архитектуры монолитного приложения

**Технологический стек:**
- **Язык программирования:** Go (использует фреймворк Gin для HTTP)
- **База данных:** PostgreSQL с простой схемой (таблица sensors)
- **Архитектура:** Монолитная - все компоненты в одном приложении
- **Взаимодействие:** Полностью синхронное, без асинхронных операций
- **Развертывание:** Docker-контейнер с одним приложением

**Структура приложения:**
- `main.go` - точка входа с инициализацией сервера и маршрутизацией
- `handlers/` - HTTP-обработчики для API датчиков
- `models/` - модели данных (Sensor)
- `services/` - сервисы для взаимодействия с внешними API
- `db/` - слой работы с базой данных

**Ограничения архитектуры:**
- Масштабирование только по принципу "всё или ничего"
- Развертывание требует остановки всего приложения
- Тесная связанность между компонентами
- Невозможность использования разных технологий для разных модулей

### 3. Определение доменов и границы контекстов

На основе анализа кода и требований к целевой системе выделены следующие домены:

**1. Device Management (Управление Устройствами)**
- Управление жизненным циклом устройств (создание, обновление, удаление)
- Хранение метаданных устройств (тип, местоположение, статус)
- Управление состоянием устройств (включено/выключено)

**2. Telemetry (Телеметрия)**
- Сбор данных с датчиков в реальном времени
- Хранение исторических данных
- Обработка и агрегация метрик

**3. Heating Control (Управление Отоплением)**
- Бизнес-логика управления отоплением
- Сценарии автоматизации
- Алгоритмы регулирования температуры

**4. Lighting Control (Управление Освещением)** *(для будущего развития)*
- Управление световыми устройствами
- Сценарии освещения

**5. Security & Access Control (Безопасность и Контроль Доступа)** *(для будущего развития)*
- Управление воротами и замками
- Видеонаблюдение
- Контроль доступа

**6. User Management (Управление Пользователями)**
- Аутентификация и авторизация
- Профили пользователей
- Привязка устройств к пользователям

### 4. Проблемы монолитного решения

**Масштабируемость:**
- Невозможность независимого масштабирования отдельных функций
- Требует выезда специалиста для подключения каждого датчика
- Ограничение в 100 клиентов и 100 модулей

**Технологические ограничения:**
- Привязка к одному языку программирования (Go)
- Единая база данных для всех доменов
- Синхронная архитектура не подходит для IoT устройств

**Развертывание и поддержка:**
- Остановка всей системы при обновлении любой части
- Сложность локализации проблем
- Единая точка отказа

**Бизнес-ограничения:**
- Невозможность самостоятельного подключения устройств пользователями
- Ограниченная функциональность (только отопление)
- Сложность добавления новых типов устройств

# Задание 3. Разработка ER-диаграммы

## Идентификация ключевых сущностей

На основе анализа микросервисной архитектуры выделены следующие основные сущности:

### Пользователи и дома:
- **User** - пользователи системы с ролями и правами доступа
- **House** - дома в системе с адресной информацией
- **Room** - комнаты в доме с типизацией
- **UserHouse** - связующая таблица для многих-ко-многим отношений пользователей и домов

### Устройства:
- **DeviceType** - типы устройств с техническими характеристиками
- **Device** - физические устройства с сетевыми параметрами
- **DeviceState** - текущие состояния устройств с историей изменений

### Телеметрия и мониторинг:
- **TelemetryData** - данные с датчиков с временными метками
- **SecurityEvent** - события безопасности с уровнями критичности

### Автоматизация:
- **HeatingSchedule** - расписания отопления по комнатам и времени
- **Scenario** - пользовательские сценарии автоматизации

### Уведомления:
- **Notification** - система уведомлений с различными методами доставки

## Описание ключевых атрибутов

### Device (Устройство):
- `id` - уникальный идентификатор UUID
- `device_type_id` - ссылка на тип устройства
- `house_id`, `room_id` - местоположение устройства
- `serial_number`, `mac_address` - идентификаторы устройства
- `status` - статус устройства (ONLINE/OFFLINE/ERROR/MAINTENANCE)
- `connection_status` - состояние подключения
- `battery_level` - уровень заряда батареи

### TelemetryData (Телеметрия):
- `device_id` - источник данных
- `sensor_type` - тип датчика (TEMPERATURE/HUMIDITY/PRESSURE и др.)
- `value` - числовое значение измерения
- `unit` - единица измерения
- `quality` - качество данных (GOOD/POOR/BAD)
- `timestamp` - временная метка
- `metadata` - дополнительные данные в JSON

## Описание связей

### Основные связи 1:N (один-ко-многим):
- **User → House**: Пользователь может владеть несколькими домами
- **House → Room**: Дом содержит несколько комнат
- **House → Device**: В доме может быть множество устройств
- **Device → TelemetryData**: Устройство генерирует множество записей телеметрии
- **Device → DeviceState**: Устройство имеет множество состояний в истории

### Связи M:N (многие-ко-многим):
- **User ↔ House** (через UserHouse): Пользователь может иметь доступ к нескольким домам, дом может быть доступен нескольким пользователям с разными ролями

### Специализированные связи:
- **DeviceType → Device**: Классификация устройств по типам
- **Room → Device**: Физическое размещение устройств в комнатах
- **HeatingSchedule**: Связывает дом, комнату и устройство отопления с расписанием

# Задание 4. Создание и документирование API

## 1. Типы API и обоснование выбора

Для экосистемы "Тёплый дом" используется гибридный подход с комбинацией REST API и Event-Driven Architecture:

### REST API (OpenAPI 3.0)
**Используется для:**
- Синхронного взаимодействия клиент-сервер
- CRUD операций с устройствами, расписаниями, сценариями
- Получения телеметрии и метрик
- Команд управления устройствами

**Преимущества:**
- Простота интеграции для веб и мобильных приложений
- Стандартизированные HTTP методы (GET, POST, PUT, DELETE)
- Автоматическая генерация клиентских библиотек из OpenAPI спецификации
- Встроенная поддержка в Spring Boot через Swagger/Springdoc

### AsyncAPI (Event-Driven)
**Используется для:**
- Асинхронного взаимодействия между микросервисами
- Публикации событий изменения состояния устройств
- Потоковой передачи телеметрии
- Системы алертов и уведомлений

**Преимущества:**
- Слабая связанность микросервисов
- Высокая производительность для IoT нагрузок
- Масштабируемость через Apache Kafka
- Надежность доставки событий

## 3. Документация AsyncAPI

[AsyncAPI спецификация Events](schemas/api/async-events-api.yaml)

События изменения состояния устройств:

## 4. Интеграция с Spring Boot

- **Spring REST Docs** + **Springdoc OpenAPI** для автоматической генерации документации

- **Spring Security** для JWT аутентификации
- **Spring Validation** для валидации запросов
- **Spring HATEOAS** для RESTful ссылок (опционально)
